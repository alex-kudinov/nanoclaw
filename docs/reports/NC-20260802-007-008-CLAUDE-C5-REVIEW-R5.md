## 1. Verdict

**CHANGES REQUIRED.**

The NC-008 half is good work and I would approve it on its own. The NC-007 half
contains one factual defect that I verified empirically against the platform,
and it has propagated into four tracked authoritative files plus two tests.

**macOS `/usr/bin/shlock` does not take over a stale lock.** I probed it
directly on this host, including the realistic case where shlock itself created
the lock and the holder then died. It detects the dead PID and _still refuses_:

```
shlock: process 39983 is dead 39983
shlock: lock time changed 1785701480 >= 0
→ exit status 1
```

Repeated invocations, an aged mtime, padded and unpadded PID formats: all refuse.
The takeover branch is unreachable on macOS because the lock-time guard compares
against a zero-initialised value, so `mtime >= 0` always aborts it.

Consequences:

1. **The documented recovery story is false** in `docs/RELEASE-INTEGRITY.md:135-137`,
   `docs/SECURITY.md:31`, `docs/ACTIVE-WORK.md:15` and `:102`, and
   `docs/ENGINEERING-CHANGELOG.md:34` and `:44-45`.
2. **R3 A1 is reopened and made worse.** The previous hand-rolled reclaim did
   recover a stale lock (with the narrow race R4 N1 flagged). The replacement
   recovers nothing, so a stale lock permanently blocks every activation —
   including `--recover-from-down`, the incident path — behind the misleading
   error `release activation lock is held by PID <dead-pid>`.
3. **Two tests validate fiction.** The `shlock` mock
   (`src/release-activation-exec.test.ts:31-41`) unconditionally unlinks any
   lock not naming the current PID, which is the inverse of real behaviour in
   two of four cases.

None of this makes the shipped code _unsafe_ — it is fail-closed, and the
concurrency property R4 N1 asked for is genuinely achieved (verified: a second
claim against a live holder returns 1). The required changes are small and
mechanical (§5). Everything else in the delta is approved.

## 2. Answers to the ten required questions

### Q1 — Does `shlock` close the double-reclaimer race, and is the handling fail-closed?

**Race: yes, closed. Stale takeover: no — it does not exist. Fail-closed: yes,
but at the cost of all recovery.**

`acquireActivationLock` (`src/release-activation-exec.ts:164-173`) delegates to
`/usr/bin/shlock -f <lock> -p <pid>`; `releaseActivationLock` (`:175-178`)
unlinks only when `readLockHolder` (`:151-157`) equals this process's PID.

I probed the real binary rather than the mock. Results on this host:

| Scenario                          | Real `shlock`      | Mock (`…-exec.test.ts:31-41`) |
| --------------------------------- | ------------------ | ----------------------------- |
| No lock present                   | claim, exit 0      | claim ✅                      |
| Lock held by **live** foreign PID | refuse, exit 1     | **takes over** ❌             |
| Lock held by **dead** foreign PID | **refuse, exit 1** | takes over ❌                 |
| Lock naming this process          | refuse, exit 1     | refuse ✅                     |

The unlink/create window R4 N1 identified is genuinely gone — `shlock` claims
via `link(2)` on a temp file, so two live activators serialize correctly, and
cleanup is owner-checked. That half is a real improvement.

But the dead-PID row is the defect. Debug output from a lock that `shlock`
itself created, whose holder then exited:

```
shlock: checking extant lock <…/t.lock>
shlock: process 39983 is dead 39983
shlock: lock time changed 1785701480 >= 0
```

`>= 0` shows the comparison is against an uninitialised lock time, so the
takeover always aborts. macOS `shlock` usage is `shlock [-du] [-p PID] -f file`
— there is no option that enables it.

_Format assumptions are fine._ `shlock` writes `"39983\n"` on this host;
`readLockHolder`'s `.trim()` also handles the classic `%10d` padded form, which
I tested. _Filesystem assumptions are fine_ — the lock lives beside the installed
plist in `~/Library/LaunchAgents`, a normal local filesystem where `link(2)` is
reliable.

_Two further fail-closed gaps, both Low:_

- **No availability probe for `shlock`.** `lsof` gets one
  (`assertListenerProbe`, `:147-149`), `shlock` does not. If `/usr/bin/shlock`
  is ever absent or non-executable, `run` throws and the catch at `:165-172`
  reports `lock is held by PID unknown` — a missing-tool failure misreported as
  contention.
- **`shlock` is only reached in apply** (`:344`), after the dry-run return, so a
  missing binary surfaces only at `--apply` — the exact asymmetry NC-007 just
  fixed for `lsof`.

### Q3 — Is per-lead serialization correct, and can duplicate roots still occur?

**Serialization is correct for success and failure. Duplicate roots are
substantially reduced but not eliminated — resolver degradation still bypasses
the lock.**

`withLeadRoutingLock` (`src/channels/slack.ts:790-804`) chains onto the prior
tail with `prior.catch(() => {}).then(operation)`, so a rejected predecessor
cannot poison the chain; the caller still receives the rejection because it
awaits `current`; and the `finally` deletes the map entry only when it is still
`current`, so a later chained caller's tail survives. There is no unhandled
rejection because `await current` attaches a handler to the stored promise.

`src/channels/slack.test.ts:1780-1836` proves the intended outcome directly: two
simultaneous identical `[FOLLOW-UP #2]` cards produce two posts, exactly one
`rollThreadAnchor`, the first at channel root and the second threaded under it.

**The residual is real and worth stating plainly.** The lock key is
`` `${jid}|${leadKey}` ``, and `src/channels/slack.ts:826-829` routes _around_ the
lock entirely when `leadKey` is undefined:

```ts
if (!leadKey) {
  await this.sendMessageRouted(jid, text, opts, undefined);
  return;
}
```

The dominant cause of a missing `leadKey` is exactly the resolver downgrade this
same change instrumented (`:723-733`). So the case that most needs
serialization — a transient business-DB failure during two simultaneous
scheduled posts (`src/channels/slack.ts:725-737`) — is the case the lock does not
cover. Those posts fall through
with no `threadKey` at all and land unanchored at channel root.

This is a pre-existing degradation, not a new one, and the direction is
fail-visible rather than fail-silent. It is correctly assigned to the new
diagnostics rather than hidden. But the delta description's "same-lead Slack
routing is serialized" should be read as "serialized whenever the lead is
resolvable".

### Q4 — Is six hours coherent given the timestamp actually stored, and is the trade-off stated accurately?

**Yes on all three counts, with one precision gap in the prompt wording.**

The window is measured against `root.timestamp`
(`src/channels/slack.ts:779-786`), and that value is a **stable creation time,
not a refreshed one**. `storeOutbound` derives it deterministically from the
Slack root `ts` (`new Date(parseFloat(ts) * 1000).toISOString()`), so even though
persistence is `INSERT OR REPLACE` (`src/db.ts:501`), re-storing the same root
recomputes the identical timestamp. Nothing refreshes it on activity. That is
the correct semantic for a cycle boundary.

_Coherence._ The events the window must admit — a duplicate cron fire, a
reconnect flush, an operator-requested revision — occur within minutes to a few
hours. The events it must exclude — the next daily follow-up, a re-cold months
later — are at least a day out. Six hours sits comfortably between, with the
degradation direction correct at both edges: a genuinely new cycle inside six
hours collapses _quietly_ (bad but narrow), while a revision after six hours
becomes a _visible_ new root (mildly noisy, never invisible).

_Failure handling is fail-safe._ `!Number.isFinite(rootAgeMs)` (unparsable
timestamp) and `rootAgeMs < 0` (clock skew) both return false, producing a new
visible root rather than a silent collapse.

_Can it collapse or split?_ Yes to both, by design and bounded:
`src/channels/slack.test.ts:1746-1778` proves a 7-hour-old `[COLD]` starts a new
cycle. The mirror case — a legitimate revision requested more than six hours
after the root — splits into a new root. Visible, so acceptable.

_Documentation._ `groups/sales/CLAUDE.md:13-18` states the rule and, correctly,
tells the agent not to force either outcome by copying an older `thread_ts`.
`docs/PROJECT-MAP.md` and `docs/ACTIVE-WORK.md` match. **One precision gap:** the
prompt says "within six hours" without saying six hours _from the root's
creation_. An agent or operator could read it as a rolling window refreshed by
activity. One clause would remove the ambiguity.

### Q5 — Can the retry timer duplicate, spin, go dormant, or reorder?

**Spin: no. Dormancy: no. Duplication: one narrow pre-existing path.
Reordering: yes, bounded and pre-existing.**

- **No spin.** `scheduleOutgoingRetry` (`src/channels/slack.ts:1580-1596`)
  returns early when a timer already exists, so failures cannot stack timers.
  Backoff is `5s · 2^attempt` capped at 5 min, and the handle is `unref`'d so it
  cannot hold the process open.
- **No permanent dormancy.** Every failure path routes through
  `queueOutgoingRetry` (`:1571-1578`), which always schedules. The flush tail
  (`:1656-1657`) resets the attempt counter on a fully drained queue and
  reschedules otherwise. When `connected` is false the scheduler deliberately
  declines, and `connect()`/`recreateApp()` call `flushOutgoingQueue` on
  reconnect — so the disconnected case is covered by the existing path, not
  orphaned. `disconnect()` clears the timer (`:1271-1274`). I traced the
  disconnect-during-pending-retry interleaving and it recovers: the timer fires,
  items re-queue as disconnected, the scheduler declines, and the reconnect flush
  picks them up.
- **Duplication.** The retry itself is exactly-once for the failure it handles.
  The one narrow path is unchanged from before: if `postMessage` **succeeds** and
  a subsequent in-`try` step throws — `storeOutbound`, or an anchor write — the
  outer catch re-queues the whole logical message and the post is duplicated.
  Pre-existing, and the same shape exists inside `sendThreadRemainder`
  (`:1598-1632`) where a `storeOutbound` throw re-queues from the already-posted
  index. Low.
- **Reordering.** `splice(0)` snapshots the batch and a failed item returns to
  the tail, so a failure reorders it relative to later successes. Pre-existing
  (recorded in R3), now also applying to `thread-remainder` items, where the
  effect is confined within one thread. Bounded.
- Verified end-to-end: `src/channels/slack.test.ts:939-962` drives a connected
  non-connection failure, advances 5 s, and asserts the second post plus a
  drained queue and a reset attempt counter.

### Q6 — Does remainder-only retry preserve unsent content exactly once, including a second failure?

**Yes, whenever a root was established. The unanchored multi-chunk case still
falls back to whole-message retry.**

On a chunk failure at `index > 0` with a live `effectiveThreadTs`
(`src/channels/slack.ts:992-1004`), only `chunks.slice(index)` is queued as a
`thread-remainder` bound to the established root, and the function returns
without touching the outer catch. `sendThreadRemainder` posts each remaining
chunk under `item.threadTs` and, on a **second** failure, re-queues
`{...item, chunks: item.chunks.slice(index)}` (`:1624-1627`) — again only the
still-unsent tail. Exactly-once holds across repeated partial failures, and no
second root can appear because the remainder carries a fixed `thread_ts` and
never re-enters the work-item branch.

The uncovered case is `index > 0` with a falsy `effectiveThreadTs` — a split
message with no anchor and no established root, where the loop `throw`s and the
outer catch re-queues the whole logical message, duplicating chunk 1. The delta
description is correctly conditional about this ("If a long post established a
root before a later chunk failed…"), so it is an accurately-scoped residual
rather than an overstatement.

### Q8 — Are the new `/health` fields non-sensitive and operationally sufficient?

**Non-sensitive: yes. Sufficient: yes for the two degradations they target.
Durability: not signalled.**

`getDiagnostics` (`src/channels/slack.ts:1256-1263`) returns four scalars —
`outgoingQueueDepth`, `outgoingRetryAttempt`, `leadResolverDowngradeCount`,
`lastLeadResolverDowngradeAt`. No lead address, message content, thread

across a deploy would read a reset as a recovery. Adding a `sinceProcessStartAt`
sibling, or naming the fields `…SinceStart`, would remove the ambiguity at no
cost. Low, and it belongs with the shipped change rather than a later one because
the field names are about to become an operator habit.

## 3. Findings

### B1 — Blocker — macOS `shlock` does not perform stale-lock takeover

Evidence and reproduction in §Q1. Four tracked files assert it (§Q9). Functional
consequence: a lock left by a killed activator permanently blocks activation,
including `--recover-from-down`, reporting `lock is held by PID <dead>`.

This regresses R3 A1 from "recovers, with a narrow race" to "never recovers".
The race is genuinely fixed; the recovery was traded away without the trade being
noticed.

**Correction:**

1. Remove the takeover claim from `docs/RELEASE-INTEGRITY.md`,
   `docs/SECURITY.md`, `docs/ACTIVE-WORK.md`, and the changelog entry; state
   that `shlock` refuses any extant lock and that a stale lock requires an
   explicit operator action.
2. Provide that action: either an explicit `--break-stale-lock` flag (race-free
   because it is operator-gated and cannot fire concurrently by accident) or a
   documented removal step in the `--recover-from-down` runbook section naming
   the exact path `<plist>.activation.lock`.
3. Improve the error at `src/release-activation-exec.ts:165-172` to report
   whether the recorded PID is alive, so a dead holder reads as
   `stale lock from PID <n>` rather than `held by PID <n>`.

### B2 — Blocker — the `shlock` mock inverts real semantics, so the core lock property is untested

`src/release-activation-exec.test.ts:31-41` unlinks any lock whose holder is not
this process, with no liveness check. Real `shlock` refuses in that case. The
mock is therefore wrong in two of four cases (§Q1 table), and the live-foreign-
activator refusal — the property the lock exists for — is not exercised anywhere.

**Correction:** make the mock refuse whenever the lock exists and its recorded
PID is alive _or_ the takeover is disallowed (i.e. mirror the real binary:
refuse whenever the file exists), add a test asserting refusal against a live
foreign PID, and rewrite the stale test to assert the real outcome — refusal —
once B1's recovery decision is made.
