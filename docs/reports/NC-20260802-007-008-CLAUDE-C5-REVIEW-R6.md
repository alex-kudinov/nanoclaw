## 2. Answers to the five questions

### Q1 — Are B1 and B2 fully closed, without a new race or misleading claim?

**Yes to all three parts.**

**Code.** `acquireActivationLock` (`src/release-activation-exec.ts:167-182`)
invokes `shlock` once and, on failure, reports one of three distinct states
without touching the file:

```
… lock is held by live PID <n>          (numeric holder, pidExists true)
… lock is stale from dead PID <n>       (numeric holder, pidExists false)
… lock has an unreadable or missing owner (<raw>)
```

There is **no unlink anywhere on the acquisition path**. `releaseActivationLock`
(`:185-188`) is unchanged and still unlinks only when the file content equals
this process's PID. The R5 B1 race is therefore structurally impossible: the
only unlink is owner-checked, and the only claim is `shlock`'s atomic `link(2)`.

**Tests.** The mock (`src/release-activation-exec.test.ts:31-40`) now mirrors the
platform exactly — `if (fs.existsSync(lockPath)) throw new Error('lock held')` —
refusing every extant lock, with a comment naming the real behaviour. That
inverts the R5 defect, where any foreign holder was silently taken over. Three
new tests cover the matrix the request specifies:

- `:211` _refuses a second activator while a live foreign PID holds the lock_ —
  uses `process.ppid`, a genuinely live foreign PID, and asserts the exact
  `held by live PID` message, an unchanged plist, and no `launchctl unload`.
  This is the property that had **no test at all** in R5.
- `:239` _refuses a stale lock until an operator verifies and removes it_ —
  asserts `stale from dead PID 2147483647`, that the lock file **still exists**
  afterwards (the no-auto-unlink invariant), and that `shlock` was actually
  invoked with the expected argv.
- `:269` _reports a failed atomic claim with no readable owner_ — asserts the
  third state.

**Docs.** All four surfaces now state the real behaviour and none claims
takeover. A repository-wide grep for `takeover` / `take over` / `stale recovery`
returns nothing outside the R5/R6 review artifacts themselves.

- `docs/RELEASE-INTEGRITY.md:135-151` — "it refuses every extant lock, including
  a stale one", plus a five-step operator recovery: prove no activation command
  is running, preserve the error output, remove only the exact reported
  `<installed-plist>.activation.lock`, restart the full dry-run — with the
  rationale stated ("the activator never auto-reclaims a stale lock because an
  unlink/reclaim sequence can delete a concurrent owner's claim").
- `docs/SECURITY.md:31-35` — same substance, correctly scoped.
- `docs/ACTIVE-WORK.md:109-121` — implementation plus an explicit R5
  reconciliation note.
- `docs/ENGINEERING-CHANGELOG.md:51-64` — records the correction and its
  provenance.

This closes B1 items 1-3 and B2 in full.

### Q4 — Is the remaining resolver degradation a deploy blocker?

**No. It is a bounded, fail-visible follow-up, and the disposition is correct.**

When the business-DB lookup fails, `deriveLeadKey` returns `undefined`, so
`src/channels/slack.ts:826-829` bypasses the per-lead serialization and the post
lands unanchored at channel root. That behaviour is unchanged by this delta.

The reasoning recorded at `docs/ACTIVE-WORK.md:84-90` is the right one: a
fallback identity would mint a second lead authority, which is precisely what
the canonical `lead:{email}` anchor exists to prevent — and it is the same
failure class the project rejected for Heartbeat submission identity under
NC-004. Trading a _visible, unanchored_ post for a _confidently wrong_ thread
would be a worse outcome.

Three properties make it acceptable to ship:

1. the failure is visible (a root post the operator sees), never silent;
2. it is now observable — `leadResolverDowngradeCountSinceStart` and
   `lastLeadResolverDowngradeAt` in `/health` are exactly this signal;
3. it requires a business-DB failure to trigger, which is itself alertable.

## 4. Follow-ups (none blocking)

### G1 — Low — the resolver fallback is deferred but has no `planned` row

`docs/ACTIVE-WORK.md:87-90` calls a fallback lead identity "a bounded follow-up".
`docs/CHANGE-PROTOCOL.md:257-259` requires every open follow-up to become a
`planned` active-work row with an owner **or** be explicitly declined with a

not be introduced; unanchored-and-observable is the accepted behaviour"), which
is what the reasoning actually supports.

### G2 — Low — `assertListenerProbe` now probes two unrelated dependencies

`src/release-activation-exec.ts:147-156`. Rename to something like
`assertHostToolProbes`. Cosmetic; the behaviour and its test are correct.

### G3 — Low — `releaseActivationLock` retains a bounded check-then-act

`src/release-activation-exec.ts:185-188` reads the holder then unlinks. If an
operator manually removed this process's lock and a new activator claimed it in
the interval, the unlink would remove the new owner's claim. R5's automatic
reclaim made this window routine; it now requires deliberate operator
intervention mid-activation, so it is an accepted residual rather than a
defect. Closing it would need an `openSync`+`fstat` inode comparison.

- A new cycle re-using the same scheduled marker inside six hours collapses
