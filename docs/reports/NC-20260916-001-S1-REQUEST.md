# NC-20260916-001 S1 necessity review — Commerce refund Bookkeeper

## Current result and constraints

Tandem Commerce 1.22.0 issued one full Adyen TEST refund for an existing internal
$1 TEST payment. Adyen returned 201, the signed `REFUND success` webhook moved
the WordPress order to refunded, and WordPress generated/emailed the internal
refund receipt. The existing refund-scoped Bookkeeper job is preserved pending
with `bookkeeper_delivery_failed` because the live NanoClaw receiver accepts
only signed `AUTHORISATION success` envelopes.

The exact live NanoClaw release is
`ebd07d52e8e7433068086b749ab023fb53ddf5c3`. It already owns one HMAC-authenticated
Commerce Bookkeeper route, one host handler, one child recorder, Payment Log,
Student Roster and `business_v2.contador_adyen_payments`. It has no Adyen refund
projection.

Constraints:

- WordPress and the retained signed Adyen refund event remain money-movement
  authority. NanoClaw must not call Adyen or infer a refund.
- Only `REFUND success` is admitted in this walking skeleton. Validation
  failure/reversal remain operator attention in WordPress and do not create a
  second outbound action here.
- Bind refund PSP, original payment PSP, refund reference, original order
  reference, exact amount/currency and cumulative/remaining amounts.
- Preserve the original Payment Log row and payment projection.
- Update only the existing Payment Log status cell to `partially refunded` or
  `refunded`; never change the original amount, provider ID, learner or date.
- Do not mutate Student Roster, access, enrollment, capacity or lifecycle.
- Append one PII-free Postgres refund projection idempotently by refund PSP.
- Reuse the existing route, signature, process, retry job and Contador channel.
- No new service, endpoint, credential, queue, worker, scheduler or customer
  communication.

Evidence required now: exact contract tests; disposable PostgreSQL migration,
idempotency and guarded rollback; payment-path regression; typecheck; immutable
release; health; and one replay of only the preserved TEST refund job with
Payment Log/Postgres/Slack/WordPress readback and no roster change.

## Operational-obligation delta

| Obligation | Before/after | Surface | Counterfactual | Proposed verdict |
| --- | --- | --- | --- | --- |
| Refund envelope branch | Receiver currently rejects all refunds; accept one exact signed successful refund using existing HMAC/freshness route | `src/commerce-bookkeeper.ts`, Tandem Commerce refund payload | Without it the existing refund job retries forever and accounting cannot reflect confirmed refunds | KEEP |
| PII-free refund projection | No durable Adyen refund record; append one row keyed by refund PSP and linked to original projected payment | migration/rollback 170, structure-only schema | Without it replay/readback cannot distinguish two partial refunds or prove accounting projection | KEEP |
| Payment Log status projection | Original payment stays `paid`; update only its status cell from cumulative signed refund truth | existing recorder child and same spreadsheet | Without it the operator's primary payment view materially overstates retained revenue | KEEP |
| Student Roster non-action | Existing payment path writes roster; refund path must explicitly skip and report unchanged | existing recorder result/summary | Reusing payment behavior would silently revoke or rewrite access/roster without authority | KEEP |
| Existing retry/recovery | One WordPress job retries existing receiver/recorder until exact readback | no new runner | A new queue/worker would duplicate operational ownership | REMOVE any new runner |

Largest avoidable burden is treating refunds like a second payment pipeline.
The smaller path is one branch in the existing signed receiver and recorder,
one narrow additive table, one status-cell update, and no roster work.
