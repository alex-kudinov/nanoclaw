# NC-20260919-002 minimum-sufficient change review

## Decision requested

Return `KEEP`, `DEFER`, `REMOVE`, or `OWNER` for each obligation below. Name
the largest avoidable operational burden and the smallest feasible path that
still proves the requested outcome. Do not redesign Commerce, Bookkeeper,
Zentact, Bizmgr, or the accounting boundary.

## Plain-language goal

Adyen TEST payments may traverse the signed Bookkeeper integration for testing,
but they must never enter the official Payment Log, Student Roster, NanoClaw
payment projection, or Capacity commitments. Real LIVE Adyen Payment Log rows
must eventually show gross, fee and net using the best already-retained fee
evidence: detailed provider fee facts when present, otherwise Zentact's exact
settled `processingCost`, plus the separately versioned Peri estimate once.

## Current observable result and authority

- Production NanoClaw is exact release `041fe20e9525`; Commerce 1.44.11 is
  active.
- Commerce already stores every order with `environment=test|live` and retains
  authenticated Zentact settlement projections including exact PSP,
  currency, match state and `processing_cost_value`.
- The signed Commerce -> NanoClaw envelope omits both environment and fee
  economics. This is a direct HTTPS signed relay; n8n is not on this path.
- Read-only production evidence shows seven recent USD 1.00 invoice payments
  with `environment=test` completed `nanoclaw.bookkeeper.notify` and were
  projected into `business_v2.contador_adyen_payments`. The owner already
  removed their visible spreadsheet rows and requested no historical repair.
- The Adyen authorization webhook does not contain final fee components.
  Commerce already implements the accepted precedence: detailed Adyen fee
  entries supersede rather than add to settled Zentact aggregate cost; Peri is
  estimated separately as fixed cents plus basis points and added once.
- Contador's Payment Log gross/fee/net values are diagnostic operational
  projections. Bizmgr/QuickBooks and provider evidence remain accounting
  authority.

## Constraints and credible hazards

- Never classify a test from amount, product name, email, PSP shape, or text.
  Only the producer-owned environment may make a TEST exclusion.
- TEST must not touch Sheets, roster, Capacity, or the official NanoClaw
  payment projection, but should still cross signature, schema, identity and
  host routing validation and produce an explicit non-ledger receipt.
- LIVE authorization often arrives before Zentact settlement. Waiting for fee
  evidence must not block the existing payment, roster, enrollment or capacity
  path.
- A delayed fee update must locate exactly one existing Adyen row by PSP,
  update only fee/net, preserve gross/identity/status/date/provider, and read
  back the arithmetic. Missing or conflicting rows stay retryable.
- An ordinary payment replay without fee evidence must never blank or regress
  previously reconciled fee/net cells.
- No guessed provider fee, no double-counted aggregate plus detailed fee, and
  no claim that estimated Peri is provider-settled.
- Preserve the existing direct signed route, job table/runner, retry model,
  Sheet, PostgreSQL tables, Slack receipt path, and producer-before-consumer
  compatibility. No new service, endpoint, queue, worker, scheduler,
  credential, provider call, payment, refund, customer message, or DDL.
