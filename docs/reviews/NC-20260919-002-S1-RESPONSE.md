# NC-20260919-002 minimum-sufficient change review — response

## Dispositions

| Obligation | Disposition | Basis |
| --- | --- | --- |
| Signed environment | `KEEP` | Load-bearing gate for the entire goal. Without a signed `environment` field, TEST and LIVE are provably indistinguishable at the trust boundary; every other disposition below depends on this one existing first. |
| Explicit TEST no-ledger outcome | `KEEP` | Required by the stated hazard ("dropping the request before the host proves only sender-side filtering"). | Signed fee-economics block with source/state/version | `KEEP` (computation), `OWNER: Commerce/Zentact` (precedence) | The precedence logic (detailed Adyen supersedes Zentact aggregate; Peri estimated and added once) already exists in Commerce per the request's own authority section. ## Largest avoidable operational burden

The "source/state/version" fee-economics block, as worded, implies a
three-dimensional provenance schema (where the fee came from, what state it's
in, and which version). Only two guarantees are actually required by the
constraints:

1. Never represent an estimated Peri fee as provider-settled (needs a
   `fee_basis`-style tag: detailed-Adyen vs. Zentact-settled vs.
   Peri-estimated).
2. Never add the Peri estimate more than once across replays.

Guarantee 2 does not need an independent version counter in the payload — it
is already satisfied by the existing-runner job dedup required in the
"Delayed fee reconciliation job" obligation ("replay inserts none"). Building
a separate version field duplicates that guarantee in a second place, which
is exactly the kind of parallel-source-of-truth drift that produces silent
arithmetic bugs later (two mechanisms disagreeing about whether Peri was
already applied). This is the largest avoidable burden in the packet: not
because the underlying requirement is wrong, but because it is proposed to be
enforced twice, by two different subsystems, for no added proof value.

## Smaller feasible path

Collapse the fee-economics block to two scalar fields plus the two exact
amounts already required for the arithmetic readback:

- `fee_basis`: enum, `detailed` | `zentact_settled` (provenance tag; answers
  "is this number settled fact or the accepted Zentato aggregate").
- `provider_fee_cents`: the exact value under whichever basis applies.
- `peri_fee_cents`: the estimate, applied exactly once — enforced solely by
  the existing job runner's replay-is-a-no-op guarantee already required for
  the delayed reconciliation job, not by a second field.

This satisfies every hazard in the constraints section (no guessed fee, no
double-count, no estimate mislabeled as settled) with one fewer field, one
fewer place to validate, and one fewer place the producer and consumer can
disagree. It does not touch Commerce's existing precedence computation,
Zentact, or the accounting boundary — it only narrows how that already-computed
result is carried across the signed envelope.

## Net effect

No proposed disposition changes from `KEEP`/`REMOVE` to `DEFER`; the packet's
own table is materially sound. The one adjustment is scope-narrowing within
the "kept" fee-economics obligation (drop the redundant version field,
attribute precedence computation to Commerce/Zentact rather than NanoClaw)
and an explicit ownership split to block a foreseeable redesign temptation on
the NanoClaw side.
