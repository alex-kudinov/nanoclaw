# NC-20260922-001 minimum-sufficient necessity review — S1 response

## Decision

**KEEP**

## Largest avoidable operational burden

One signed, paid USD 999 MCS Practicum installment is permanently stuck: the
receiver's cohort validator hard-codes `program ∈ {acc, pcc, actc}`, `module ∈
[1,4]`, and `sessions.length === 4` (`src/commerce-bookkeeper.ts:182-198`). The
canonical MCS envelope (`program=mcs-practicum`, `module=0`,
`enrollmentScope=full_program`, 12 sessions) fails all three checks
simultaneously and is rejected before any Bookkeeper write, confirming the
packet's claim. Absent a fix, the job retries forever with no path to success
— that's the avoidable burden: one stuck receipt plus indefinite retry noise
from a receiver that can never accept this shape.

## Smallest feasible path

Extending `prepareCommerceBookkeeperEnvelope`'s cohort branch in
`src/commerce-bookkeeper.ts` to admit the MCS shape is correctly scoped and
consistent with prior precedent (NC-20260915-002, NC-20260917-002 both
extended this same validator for new signed cohort shapes with no new
topology). `tools/contador/process-commerce-payment.cjs` needs no change:
`cohortRosterValue` (`tools/contador/process-commerce-payment.cjs:83-86`) and
the roster-write path treat `fact.cohort.rosterValue` generically — roster
destination comes from the Product Map via `productId`
(`facts/generated/student-product-bindings-v2.scoped.json` — `mcs-full` →
tab `MCS`, column `MCS Practicum`), not from `cohort.program`. Stage 1's file
scope (validator + focused test + continuity docs) is sufficient for the
recovery half of the work.

## Material finding

The packet's phrase "extend the bounded cohort union" is easy to
under-implement in a way that silently fails or over-widens scope, because
the current validator shares one set of range checks across all programs:

- **Key shape differs, not just the enum.** The existing regex is
  `^${program}-m${module}-[a-f0-9]{24}$` (line 187), i.e. every accepted
  program's key embeds `-m{module}-`. The packet states the actual signed MCS
  key is `mcs-practicum-<24 hex>` — no module segment. A naive fix that adds
  `'mcs-practicum'` to the program list while reusing this same regex
  template will keep rejecting the exact envelope it's meant to recover.
- **Shared bounds, not per-program bounds.** `module` range (`1-4`),
  `sessions.length === 4`, and the array-typed program check are all single
  shared conditions (lines 182-198), not branched per program. Widening them
  in place to admit `module=0` / 12 sessions for MCS — instead of adding a
  distinct MCS-shaped branch — would also let ACC/PCC/ACTC envelopes present
  `module=0` or a 12-session `full_program` cohort, which is exactly the
  "permissive generic cohort acceptance could route fabricated metadata"
  hazard the packet already warns against in its own constraints section.

This doesn't change the KEEP decision — the recovery is real, bounded, and
follows an established, low-risk pattern — but Stage 1's implementation must
add a distinct MCS-shaped branch (own key regex, own module/session/scope
values) rather than loosen the existing acc/pcc/actc bounds in place. Flag
this for the implementer and for S2 review before the first live recovery
attempt.
